So you have a Netcup server with Plesk, a static site served by Apache, and — for the first time — a real Node app to run alongside it. This guide walks through exactly that, using this very wiki as the example.

By the end, editing a Markdown file and pushing to `main` rebuilds the site and streams it to the server. Then one click in Plesk restarts the app. Roughly a minute from push to live.

::note
This is the successor to the old Astro wiki's deploy guide. The pipeline shape is the same — build in CI, backup before deploy, keep the portal at `/` and the wiki in a subfolder — only now a Node process serves the site instead of flat HTML files.
::

## The whole pipeline

```text [Architecture]
┌──────────────┐   push to main   ┌───────────────────┐
│   GitHub     │ ────────────────►│  GitHub Actions   │
│  (this repo) │                  │  pnpm build       │
│  .md files   │                  │  backup server    │
└──────────────┘                  │  tar .output/ ►SSH│
                                  └─────────┬─────────┘
                                            │
                                            ▼
                               ┌──────────────────────────┐
                               │    Netcup server          │
                               │                           │
                               │  Plesk Node.js manager    │
                               │  runs the app at /docus/  │
                               │  (root: httpdocs)         │
                               └──────────────────────────┘
```

Key idea: Plesk's Node.js manager runs the wiki app, and the portal keeps being served at `/` from static files. `/docus/*` is routed to the Node app by Plesk.

## Why a Node app at all?

- **Server-side rendering** — pages are rendered per request, so routes like `/mcp` and runtime OG images keep working (a static build can't).
- **This is a learning milestone** — running a real Node process behind the web server is the same pattern used by thousands of production apps.

The trade-off: you now manage a running process. On this hosting the process is managed by **Plesk**, not you.

## Prerequisites

- The **Netcup server** with Plesk (Node.js app support) and SSH access
- The **portal** already served at `/` (static files, existing `.htaccess` with the HTTPS/www redirects)
- This wiki's repo on **GitHub** (`simkne/weltkugl-wiki`)
- Local access to generate an SSH key

## Step 1 — Understand the server layout

This hosting is **Plesk**, and the SSH account is **chrooted**: the server's real path
`/var/www/vhosts/hostingxxx.xxxx.mydomain.net/` appears as **`/`** inside the SSH shell.

Consequences that matter:

- **`node` is NOT reachable from SSH.** It lives at the host (`/opt/plesk/node`) outside the chroot. `node`, `npm`, and `pm2` commands will fail with *"command not found"* or `/usr/bin/env: 'node': No such file or directory`. Do not try to run the app from SSH — Plesk does that.
- The app lives at **`/mydomain.net/httpdocs/docus`** (chroot-relative path). The real absolute path is `/var/www/vhosts/hostingxxx.xxxx.mydomain.net/httpdocs/docus`.
- Because the app root is `httpdocs` (the domain root), the wiki is a subfolder inside it: `httpdocs/docus`.

Verify the layout:

```bash [Terminal]
ssh your-user@your-server
find ~ -maxdepth 3 -type d -name "docus" 2>/dev/null
# → /weltkugl.net/httpdocs/docus
```

## Step 2 — Create a deploy-only SSH key

Generate a key pair on your local machine, used only by CI — never your personal key:

```bash [Terminal]
ssh-keygen -t edxxxx -C "github-actions-docus-deploy" -f ~/.ssh/docus_deploy
# Press Enter twice — no passphrase (CI can't type one)
```

Two files are created:

- `~/.ssh/docus_deploy` — **private key** → goes into GitHub as a secret
- `~/.ssh/docus_deploy.pub` — **public key** → goes on the server

Install the public key on the server:

```bash [Terminal]
ssh-copy-id -i ~/.ssh/docus_deploy.pub your-user@your-server
# or manually:
echo "$(cat ~/.ssh/docus_deploy.pub)" >> ~/.ssh/authorized_keys
```

Test it logs in without a password:

```bash [Terminal]
ssh -i ~/.ssh/docus_deploy your-user@your-server
```

## Step 3 — Configure the app in Plesk

The app is enabled in the **Plesk panel**, not via config files on disk:

1. **Plesk → Domains → mydomain.net → Node.js**
2. Enable Node.js for the domain.
3. **Application root**: `httpdocs` (the domain root — Plesk pins this, you may not be able to change it)
4. **Application startup file**: `docus/.output/server/index.mjs`
5. Save, then use the **Restart** button.

The startup file is what Plesk executes with node. If it's wrong, `/docus/` returns 500 — the classic symptom. Fixing the startup file path (and restarting) is what makes the site appear.

::warning
After **every** deploy the app must be restarted in Plesk (Node.js section → Restart). There is no SSH-reachable way to restart it, and it does not reliably auto-reload. The old process keeps serving stale code until you restart.
::

## Step 4 — GitHub Actions secrets

In the repo: **Settings → Secrets and variables → Actions → New repository secret**. Four secrets:

| Secret | Value |
| --- | --- |
| `SSH_HOST` | `hosting123456.xxxxxx.server.net` (or the IP) |
| `SSH_USERNAME` | The web/SSH user the deploy key authenticates as |
| `SSH_PRIVATE_KEY` | Full contents of `~/.ssh/docus_deploy` (from `-----BEGIN` to `-----END`) |
| `DEPLOY_PATH` | `/domain.net/httpdocs/docus` — **chroot-relative**, must match where `.output/` lands |

## Step 5 — The workflow (already in the repo)

`.github/workflows/deploy.yml` runs on every push to `main` and does:

1. **Install & build** — `pnpm install --frozen-lockfile` then `pnpm build`, with `NUXT_SITE_URL=https://mydomain.net` (domain only; `/docus/` comes from `app.baseURL`). The build runs on **ubuntu-latest (Linux x64)** — a macOS build must never be uploaded, it ships `@img/sharp-darwin-arm64` binaries that won't run on Linux.
2. **Backup** — inlined in the workflow (no server script). If `.output/` exists, it tars it to `backups/backup-<timestamp>.tar.gz` and keeps the last 5. First deploy skips.
3. **Deploy** — streams `.output/` (including `node_modules` — the whole Linux build) over SSH with `tar`, clearing the previous `.output/` first so no stale chunks linger. Also ships `ecosystem.config.cjs`.
4. **No restart step** — the app is Plesk-managed and unreachable from SSH. Restart manually in Plesk after each deploy.

::note
The original plan used `rsync` and a pm2 restart step. Both were removed: `rsync` wasn't installed on the server (tar-over-SSH needs nothing), and `node`/`pm2` aren't reachable from the chrooted SSH account (Plesk runs the process).
::

## Step 6 — First deploy

1. Commit everything (including `.github/workflows/deploy.yml`, `ecosystem.config.cjs`, `app.config.ts`).
2. Push to `main`.
3. Open the **Actions** tab and watch the run — the build + backup + deploy steps should go green.
4. In **Plesk → Node.js**, restart the app.
5. Visit `https://www.weltkugl.net/docus/` — the wiki should render.

The first run logs "No previous build to back up" — that's expected.

## Day to day

1. Write a Markdown note in `content/`.
2. Commit and push.
3. The Action builds, backs up, deploys.
4. Restart the app in Plesk (one click).
5. Hard-refresh the live URL.

## When something breaks

SSH in and roll back from a workflow backup. Backups live in `backups/` next to the app:

```bash [Terminal]
ssh your-user@your-server
ls -lht /mydomain.net/httpdocs/docus/backups/
# pick a backup-*.tar.gz, then:
cd /mydomain.net/httpdocs/docus
tar -xzf backups/backup-<timestamp>.tar.gz -C /tmp/rollback
rm -rf .output && mv /tmp/rollback/.output .
```

Then restart the app in Plesk.

## Troubleshooting

| Symptom | Likely cause |
| --- | --- |
| `Permission denied (publickey)` in Actions | Secret private key ≠ public key on server. Re-add the `.pub` key. |
| `/docus/` returns 500 | App startup file wrong in Plesk, or app not restarted after deploy. |
| `/docus/` returns 502/503 | The Node app isn't running — restart it in Plesk. |
| Site works but assets 404 | `app.baseURL` mismatch — both the build and Plesk routing must use `/docus/`. |
| Changes pushed but site is old | App wasn't restarted in Plesk, or the deploy step failed — check the Actions log. |
| `node: command not found` over SSH | Expected — node is outside the chroot. Plesk runs the app, you don't. |
| Portal page redirects to `/docus/` | A blanket redirect in `.htaccess` — remove it; only the specific `/docus/` route should proxy. |

## Recap

1. Deploy-only SSH key → server + GitHub secrets
2. App enabled in Plesk (root `httpdocs`, startup `docus/.output/server/index.mjs`)
3. Workflow: install → build → backup → tar-over-SSH deploy
4. Restart the app in Plesk after each deploy
5. Push to `main` and stop thinking about deployment

You now run your first Node.js app on the server — supervised by Plesk, fed by GitHub Actions. Future Nuxt apps are a copy-paste of this same shape.
