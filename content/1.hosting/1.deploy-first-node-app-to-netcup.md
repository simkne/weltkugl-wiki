So you have a Netcup server running Apache with static files, Node.js installed, and — for the first time — a real Node app to run on it. This guide walks through exactly that, using this very wiki as the example.

By the end, editing a Markdown file and pushing to `main` rebuilds the site, rsyncs it to the server, and restarts the app. Roughly a minute from push to live.

::note
This is the successor to the old Astro wiki's deploy guide. The pipeline shape is the same — build in CI, backup before deploy, keep the portal at `/` and the wiki in a subfolder — only now a Node process serves the site instead of flat HTML files.
::

## The whole pipeline

```text [Architecture]
┌──────────────┐   push to main   ┌───────────────────┐
│   GitHub     │ ────────────────►│  GitHub Actions   │
│  (this repo) │                  │  pnpm build       │
│  .md files   │                  │  backup server    │
└──────────────┘                  │  rsync .output/   │
                                  └─────────┬─────────┘
                                            │
                                            ▼
                               ┌──────────────────────────┐
                               │    Netcup server          │
                               │                           │
                               │  Apache (portal at /)     │
                               │   └─ ProxyPass /docus/ ──►│
                               │                           │
                               │  pm2 → node (this wiki)   │
                               │  on 127.0.0.1:3001        │
                               └──────────────────────────┘
```

Key idea: Apache keeps serving the portal at `/` from static files, and only forwards `/docus/*` to the Node process listening on `127.0.0.1:3001`.

## Why a Node app at all?

- **Server-side rendering** — pages are rendered per request, so routes like `/mcp` and runtime OG images keep working (a static build can't).
- **This is a learning milestone** — running a real Node process behind the web server is the same pattern used by thousands of production apps. Once this works, any Nuxt (or Express, Fastify, …) app deploys the same way.

The trade-off: you now manage a running process. `pm2` keeps it alive, restarts it on crash, and brings it back after a server reboot.

## Prerequisites

- The **Netcup server** with SSH access and Node.js installed (it is)
- The **portal** already served at `/` (static files, existing `.htaccess` with the HTTPS/www redirects)
- This wiki's repo on **GitHub** (`simkne/…`)
- Local access to generate an SSH key

## Step 1 — Verify Node and install pm2

SSH into the server and check what's there:

```bash [Terminal]
ssh your-user@your-server

node --version
npm --version
```

Then install pm2 globally:

```bash [Terminal]
npm install -g pm2
pm2 -v
```

pm2 (Process Manager 2) supervises the Node process: restart on crash, log collection, and `pm2 startup` makes it survive reboots.

## Step 2 — Create a deploy-only SSH key

Generate a key pair on your local machine, used only by CI — never your personal key:

```bash [Terminal]
ssh-keygen -t ed25519 -a 100 -f ~/.ssh/github_deploy -C "github-actions"
# Press Enter twice — no passphrase (CI can't type one)
```

Two files are created:

- `~/.ssh/github_deploy` — **private key** → goes into GitHub as a secret
- `~/.ssh/github_deploy.pub` — **public key** → goes on the server

Install the public key on the server as the user that will own the app files:

```bash [Terminal]
ssh-copy-id -i ~/.ssh/github_deploy.pub your-user@your-server
```

Test it logs in without a password:

```bash [Terminal]
ssh -i ~/.ssh/github_deploy your-user@your-server
```

## Step 3 — Create the app directory

Pick a home for the app. `/var/www/weltkugl.net/docus` matches the existing layout (the old wiki lived at `…/www`). The directory must be writable by the deploy user:

```bash [Terminal]
ssh your-user@your-server
sudo mkdir -p /var/www/weltkugl.net/docus
sudo chown -R your-user:your-user /var/www/weltkugl.net/docus
```

::warning
The physical folder does not have to sit in the web root — Apache proxies `/docus/` to the Node app and never serves files from this directory. Putting it outside `htdocs` is fine too; you only need to adjust the path in `ecosystem.config.cjs` and the `DEPLOY_PATH` secret.
::

## Step 4 — Tell Apache to proxy /docus/

The wiki app is baked with `baseURL: '/docus/'` (see `nuxt.config.ts`), so it answers only at `/docus/...`. Apache must forward those requests to the Node port.

`ProxyPass` only works in the **virtual host or server config**, not in `.htaccess`. Open the vhost for `weltkugl.net` (usually `/etc/apache2/sites-available/…conf`) and add, inside the `<VirtualHost>`:

```apache [Apache vhost]
# Reverse proxy: /docus/ → Nuxt (pm2) app
ProxyPreserveHost On
ProxyPass        /docus/  http://127.0.0.1:3001/docus/
ProxyPassReverse /docus/  http://127.0.0.1:3001/docus/
```

Enable the proxy modules and reload Apache:

```bash [Terminal]
sudo a2enmod proxy proxy_http
sudo systemctl reload apache2
```

::tip
Leave the existing `.htaccess` redirects (HTTPS, www, bot blocking) untouched. Nothing here redirects everything to a subfolder — that old blanket-`RedirectMatch` bug is what killed the portal once. Don't reintroduce it.
::

## Step 5 — The pm2 app definition

`ecosystem.config.cjs` in the repo describes the app to pm2:

```js [ecosystem.config.cjs]
module.exports = {
  apps: [
    {
      name: 'docus-wiki',
      script: '.output/server/index.mjs',
      cwd: '/var/www/weltkugl.net/docus',
      instances: 1,
      exec_mode: 'fork',
      autorestart: true,
      max_memory_restart: '300M',
      env: {
        NODE_ENV: 'production',
        HOST: '127.0.0.1',
        PORT: 3001,
      },
    },
  ],
}
```

What each bit means:

- `script` — the built Nuxt server entrypoint. Nitro compiles the whole app into `.output/server/index.mjs`.
- `cwd` — where `.output/` lives on the server. Keep it in sync with the `DEPLOY_PATH` secret.
- `instances: 1` + `exec_mode: 'fork'` — a single process; this app is tiny and pm2's default cluster mode buys nothing here.
- `autorestart` — pm2 brings it back if it crashes.
- `max_memory_restart` — a safety valve; restart if the process leaks past 300 MB.
- `HOST`/`PORT` — bind to localhost only, so nothing but Apache can reach it. The port must match the vhost proxy target.
- `NODE_ENV: 'production'` — Nuxt runs its production code path.

## Step 6 — Backup and rollback scripts

Before every deploy the workflow snapshots the current app, so a bad release is one command away from undone.

On the server, create `~/scripts/backup-docus.sh`:

```bash [Terminal]
mkdir -p ~/scripts
```

```bash [backup-docus.sh]
#!/bin/bash
set -e

APP_PATH="/var/www/weltkugl.net/docus"
BACKUP_DIR="$HOME/docus-backups"
RETAIN_DAYS=14

mkdir -p "$BACKUP_DIR"
TIMESTAMP=$(date +%Y%m%d-%H%M%S)
BACKUP_NAME="docus-${TIMESTAMP}.tar.gz"
BACKUP_PATH="$BACKUP_DIR/$BACKUP_NAME"

# Nothing to back up on the very first deploy
if [ ! -d "$APP_PATH/.output" ] || [ -z "$(ls -A "$APP_PATH/.output" 2>/dev/null)" ]; then
  echo "No previous build to back up. Skipping."
  exit 0
fi

echo "Backing up $APP_PATH → $BACKUP_PATH"
# node_modules is reinstalled from package.json, no need to tar it
tar -czf "$BACKUP_PATH" -C "$(dirname "$APP_PATH")" \
  --exclude="docus/node_modules" \
  "$(basename "$APP_PATH")"

# Prune backups older than 14 days
find "$BACKUP_DIR" -maxdepth 1 -name 'docus-*.tar.gz' -mtime +$RETAIN_DAYS -delete
ls -lht "$BACKUP_DIR"
```

```bash [Terminal]
chmod +x ~/scripts/backup-docus.sh
```

And `~/scripts/rollback-docus.sh` — restore a backup, then restart pm2:

```bash [rollback-docus.sh]
#!/bin/bash
set -e

APP_PATH="/var/www/weltkugl.net/docus"
BACKUP_DIR="$HOME/docus-backups"

echo "Available backups:"
ls -lht "$BACKUP_DIR"/docus-*.tar.gz 2>/dev/null || { echo "No backups found."; exit 1; }

if [ -z "$1" ]; then
  BACKUP_FILE=$(ls -t "$BACKUP_DIR"/docus-*.tar.gz | head -n 1)
  echo "Using latest: $(basename "$BACKUP_FILE")"
else
  BACKUP_FILE="$BACKUP_DIR/$1"
  [ -f "$BACKUP_FILE" ] || { echo "Backup not found: $1"; exit 1; }
fi

read -p "This will wipe $APP_PATH and restore from $(basename "$BACKUP_FILE"). Continue? [y/N] " confirm
[[ "$confirm" =~ ^[yY] ]] || { echo "Aborted."; exit 0; }

# Snapshot the current (broken) state before wiping, just in case
if [ -d "$APP_PATH/.output" ]; then
  tar -czf "$BACKUP_DIR/pre-rollback-$(date +%Y%m%d-%H%M%S).tar.gz" \
    -C "$(dirname "$APP_PATH")" --exclude="docus/node_modules" "$(basename "$APP_PATH")"
fi

rm -rf "$APP_PATH"
mkdir -p "$APP_PATH"
tar -xzf "$BACKUP_FILE" -C "$(dirname "$APP_PATH")" --strip-components=1

pm2 restart docus-wiki
echo "Restored from $(basename "$BACKUP_FILE") and restarted the app."
```

```bash [Terminal]
chmod +x ~/scripts/rollback-docus.sh
```

## Step 7 — GitHub Actions secrets

In the repo: **Settings → Secrets and variables → Actions → New repository secret**. Four secrets:

| Secret | Value |
| --- | --- |
| `SSH_HOST` | Server IP or `www.weltkugl.net` |
| `SSH_USERNAME` | The SSH user that owns the app directory |
| `SSH_PRIVATE_KEY` | Full contents of `~/.ssh/github_deploy` (from `-----BEGIN` to `-----END`) |
| `DEPLOY_PATH` | `/var/www/weltkugl.net/docus` — must match `cwd` in `ecosystem.config.cjs` |

## Step 8 — The workflow (already in the repo)

`.github/workflows/deploy.yml` runs on every push to `main` and does:

1. **Install & build** — `pnpm install` then `pnpm build`, with `NUXT_SITE_URL=https://weltkugl.net/docus` so the prerendered sitemap and `/llms.txt` use absolute URLs.
2. **Backup** — SSHes in and runs `~/scripts/backup-docus.sh`.
3. **Deploy** — rsyncs `.output/` (minus `node_modules`) and `ecosystem.config.cjs` to `DEPLOY_PATH`.
4. **Restart** — installs prod dependencies in `.output/server`, then `pm2 restart docus-wiki` (or `pm2 start` on the first run, then `pm2 save`).

::note
`--delete` in the rsync removes stale chunks from previous builds. The pre-deploy backup is what makes that safe.
::

## Step 9 — First deploy

1. Commit everything (including `.github/workflows/deploy.yml` and `ecosystem.config.cjs`).
2. Push to `main`.
3. Open the **Actions** tab and watch the run — it should go green in about a minute.
4. On the server, confirm the app is up:

```bash [Terminal]
pm2 list
pm2 logs docus-wiki
```

5. Visit `https://www.weltkugl.net/docus/` — the wiki should render, served by your Node process.

The first run logs "No previous build to back up" — that's expected.

## Day to day

1. Write a Markdown note in `content/`.
2. Commit and push.
3. The Action builds, backs up, deploys, restarts.
4. Hard-refresh the live URL.

No FTP, no manual SSH for typo fixes. That's the whole point of the old wiki's "boring pipeline": the hard part stays the writing.

## When something breaks

SSH in and roll back with one command:

```bash [Terminal]
~/scripts/rollback-docus.sh              # latest backup
~/scripts/rollback-docus.sh docus-20260101-120000.tar.gz   # specific one
```

The script snapshots the current broken state first, so you can undo a bad rollback too.

## Troubleshooting

| Symptom | Likely cause |
| --- | --- |
| `Permission denied (publickey)` in Actions | Secret private key ≠ public key on server. Re-add the `.pub` key. |
| `/docus/` returns 502/503 | The Node app isn't running — `pm2 list`; check `pm2 logs docus-wiki`. |
| Site works but assets 404 | `app.baseURL` mismatch — both the build and the proxy must use `/docus/`. |
| Changes pushed but site is old | Workflow didn't finish, or the rsync/restart step failed — check the Actions log. |
| Port already in use | Something else listens on 3001 — change `PORT` in `ecosystem.config.cjs` **and** the vhost proxy target. |
| App restarts in a loop | Usually a missing prod dependency — run `npm install --omit=dev` inside `.output/server` manually and check logs. |
| Portal page redirects to `/docus/` | A blanket redirect in `.htaccess` — remove it; only the specific `/docus/` proxy should exist. |

## Recap

1. Deploy-only SSH key → server + GitHub secrets
2. App directory + `ecosystem.config.cjs` for pm2
3. Apache reverse proxy for `/docus/` (vhost, not `.htaccess`)
4. Backup / rollback scripts on the server
5. Workflow: install → build → backup → rsync → pm2 restart
6. Push to `main` and stop thinking about deployment

You now run your first Node.js app on the server. Future Nuxt apps are a copy-paste of this same shape.
