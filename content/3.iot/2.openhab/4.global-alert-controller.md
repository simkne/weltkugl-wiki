# Global Alert Controller

Subsystem rules should not each invent their own notification logic. The global alert controller gives every device one place to report a problem, and one place to decide how that problem is shown, logged, acknowledged, and delivered.

::note
This is a Main UI pattern verified against openHAB 5.2.0. Create the Items in **Settings → Items** and paste the rules into **Settings → Automation → Rules → + → Code**.
::

## Understand the pattern

The controller has three layers:

1. **Alert source** — a `Switch` Item that a subsystem sets to `ON` while a problem exists.
2. **Alert bus** — a Group Item (`gAlerts`) that contains every alert source.
3. **Alert handler** — one rule that reacts to any member of `gAlerts`, calculates the highest severity, and updates the global alert Items.

```text
Device rule ──> Alert Switch (member of gAlerts)
                         │
                         ▼
              Global Alert Collector
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
     GlobalAlert_*     openHAB log    Notify rule
     (UI state)                      (optional push)
```

The source Item is the single source of truth. The controller never clears a source alert on its own; the subsystem clears it when the condition is resolved.

## Create the alert bus

Create one Group Item:

| Item | Type | Label | Settings |
|------|------|-------|----------|
| `gAlerts` | Group | Active Alerts | Group type `Switch`, aggregation `OR(ON,OFF)`, category `Alarm` |

The `OR(ON,OFF)` aggregation makes `gAlerts.state` equal `ON` while at least one member is `ON`. That is handy for a quick “any alert active?” check in the UI or another rule.

In Main UI:

1. **Settings → Items → +**
2. Name: `gAlerts`
3. Label: `Active Alerts`
4. Type: `Group`
5. Group type: `Switch`
6. Aggregation function: `OR(ON,OFF)`
7. Save.

## Create the global alert Items

These Items hold the current summary. Add them to a logical group if you like, but they do not need to be members of `gAlerts`.

| Item | Type | Label | Purpose |
|------|------|-------|---------|
| `GlobalAlert_Active` | Switch | Alert Active | `ON` while any source alert is active |
| `GlobalAlert_Level` | String | Alert Level | `INFO`, `WARN`, or `CRITICAL` |
| `GlobalAlert_Source` | String | Alert Source | Item name of the selected alert |
| `GlobalAlert_Message` | String | Alert Message | Human-readable alert text |
| `GlobalAlert_Time` | DateTime | Alert Time | Last alert change |
| `GlobalAlert_Count` | Number | Active Alerts | Number of active source alerts |
| `GlobalAlert_Ack` | Switch | Acknowledge | Command `ON` to acknowledge |
| `GlobalAlert_Acknowledged` | Switch | Acknowledged | Ack state; new alerts reset it |
| `GlobalAlert_Clear` | Switch | Clear All | Command `ON` to clear all sources |
| `GlobalAlert_Notify` | Switch | Send Notifications | Enables the push handler |
| `GlobalAlert_NotifyTrigger` | Switch | Notify Trigger | Internal trigger for new alerts |

`GlobalAlert_Level` should have state options `INFO`, `WARN`, and `CRITICAL`. `GlobalAlert_Notify` can stay `OFF` while you are only using the UI and log.

## Add an alert source

An alert source is any `Switch` Item that is a member of `gAlerts`. Add optional metadata so the controller can show a useful message and severity.

::warning
Alert source Items are standalone state markers. Do not link them to a Thing channel. If the Item is linked to a device, the device can overwrite the alert state and the controller will see false transitions.
::

### Example Item

```text
Switch KitchenHeater_Alert_Temperature "Kitchen heater temperature" <alarm> (gAlerts) {
    alert="" [severity="CRITICAL", message="Kitchen heater temperature sensor is stale"]
}
```

If you create the Item in Main UI:

1. Create a `Switch` Item.
2. Add it to the `gAlerts` group.
3. Add metadata with namespace `alert`.
4. Leave the metadata value empty.
5. Add configuration keys:
   - `severity` = `CRITICAL` (or `WARN` / `INFO`)
   - `message` = `Kitchen heater temperature sensor is stale`

If metadata is missing, the controller falls back to `WARN` and the Item label. That means a minimal alert Item needs no metadata at all.

### Raise and clear it

From the subsystem rule:

```text
// Problem detected
KitchenHeater_Alert_Temperature.postUpdate(ON)

// Problem resolved
KitchenHeater_Alert_Temperature.postUpdate(OFF)
```

Use `postUpdate`, not `sendCommand`. The alert Item is a state marker, not a device command. Do not set it `ON` every minute; the state change is what triggers the controller. Setting an already-`ON` Item to `ON` again produces no new event.

Clear the alert only when the condition is actually resolved. Clearing it immediately after notifying would hide a fault that is still present.

## Write the central rules

Create these four Main UI rules.

### Collect alerts

```yaml
uid: global_alert_collect
label: Global Alert Collector
description: Collects alert members and updates the global alert summary
configuration: {}
triggers:
  - id: "1"
    configuration:
      groupName: gAlerts
      state: ON
    type: core.GroupStateChangeTrigger
  - id: "2"
    configuration:
      groupName: gAlerts
      state: OFF
    type: core.GroupStateChangeTrigger
  - id: "3"
    configuration:
      startlevel: 100
    type: core.SystemStartlevelTrigger
conditions: []
actions:
  - inputs: {}
    id: "4"
    configuration:
      type: application/vnd.openhab.dsl.rule
      script: |
        val active = gAlerts.members.filter[ i | i.state == ON ].toList
        GlobalAlert_Count.postUpdate(active.size)

        if (active.size == 0) {
            GlobalAlert_Active.postUpdate(OFF)
            GlobalAlert_Source.postUpdate("")
            GlobalAlert_Message.postUpdate("")
            GlobalAlert_Acknowledged.postUpdate(OFF)
            logInfo("Alerts", "All alerts cleared")
        } else {
            var level = "INFO"
            var sourceItem = active.get(0)

            for (item : active) {
                val meta = item.getMetadata("alert")
                val sev = if (meta != null && meta.config.get("severity") != null) {
                    meta.config.get("severity").toString().toUpperCase()
                } else {
                    "WARN"
                }

                if (sev == "CRITICAL") {
                    level = "CRITICAL"
                    sourceItem = item
                } else if (sev == "WARN" && level != "CRITICAL") {
                    level = "WARN"
                    sourceItem = item
                }
            }

            val meta = sourceItem.getMetadata("alert")
            val message = if (meta != null && meta.config.get("message") != null) {
                meta.config.get("message").toString()
            } else if (sourceItem.label != null) {
                sourceItem.label
            } else {
                sourceItem.name
            }

            GlobalAlert_Active.postUpdate(ON)
            GlobalAlert_Level.postUpdate(level)
            GlobalAlert_Source.postUpdate(sourceItem.name)
            GlobalAlert_Message.postUpdate(message)
            GlobalAlert_Time.postUpdate(new DateTimeType())

            if (level == "CRITICAL") {
                logError("Alerts", "CRITICAL: " + message + " [" + sourceItem.name + "]")
            } else if (level == "WARN") {
                logWarn("Alerts", "WARN: " + message + " [" + sourceItem.name + "]")
            } else {
                logInfo("Alerts", "INFO: " + message + " [" + sourceItem.name + "]")
            }

            if (triggeringItem != null && triggeringItem.state == ON) {
                GlobalAlert_Acknowledged.postUpdate(OFF)
                GlobalAlert_NotifyTrigger.postUpdate(ON)
            }
        }
    type: script.ScriptAction
```

The controller picks the highest severity among all active alerts. If any active alert is `CRITICAL`, the summary level is `CRITICAL`. Otherwise a `WARN` wins over `INFO`.

### Acknowledge

Acknowledging marks the current alert as seen and suppresses notifications. It does not clear the underlying condition.

```yaml
uid: global_alert_ack
label: Global Alert Acknowledge
description: Acknowledge the current alert without clearing the source
configuration: {}
triggers:
  - id: "1"
    configuration:
      itemName: GlobalAlert_Ack
      command: ON
    type: core.ItemCommandTrigger
conditions: []
actions:
  - inputs: {}
    id: "2"
    configuration:
      type: application/vnd.openhab.dsl.rule
      script: |
        if (GlobalAlert_Active.state == ON) {
            GlobalAlert_Acknowledged.postUpdate(ON)
            logInfo("Alerts", "Alerts acknowledged")
        }
        GlobalAlert_Ack.postUpdate(OFF)
    type: script.ScriptAction
```

### Clear all

Clearing sets every active source alert to `OFF`. Use it for testing or after fixing a problem. If the condition is still present, the subsystem will raise the alert again on its next evaluation.

```yaml
uid: global_alert_clear
label: Global Alert Clear All
description: Manually clear every active source alert
configuration: {}
triggers:
  - id: "1"
    configuration:
      itemName: GlobalAlert_Clear
      command: ON
    type: core.ItemCommandTrigger
conditions: []
actions:
  - inputs: {}
    id: "2"
    configuration:
      type: application/vnd.openhab.dsl.rule
      script: |
        for (item : gAlerts.members) {
            if (item.state == ON) {
                item.postUpdate(OFF)
            }
        }
        GlobalAlert_Clear.postUpdate(OFF)
        logWarn("Alerts", "All alerts cleared manually")
    type: script.ScriptAction
```

### Notify

This is the single place for push notifications. The collector already writes to `openhab.log`; this rule is only for an external channel.

```yaml
uid: global_alert_notify
label: Global Alert Notify
description: Central notification handler for new alerts
configuration: {}
triggers:
  - id: "1"
    configuration:
      itemName: GlobalAlert_NotifyTrigger
      state: ON
    type: core.ItemStateChangeTrigger
conditions: []
actions:
  - inputs: {}
    id: "2"
    configuration:
      type: application/vnd.openhab.dsl.rule
      script: |
        if (GlobalAlert_Active.state == ON &&
            GlobalAlert_Notify.state == ON &&
            GlobalAlert_Acknowledged.state != ON) {
            val message = GlobalAlert_Level.state + ": " + GlobalAlert_Message.state +
                " (" + GlobalAlert_Count.state + " active)"
            // Replace this log line with your notification action.
            logWarn("Alerts", "NOTIFY: " + message)
        }
        GlobalAlert_NotifyTrigger.postUpdate(OFF)
    type: script.ScriptAction
```

Keep `GlobalAlert_Notify = OFF` while you are testing. Turn it on after you replace the placeholder log line with your notification add-on action. Because the trigger is reset every time, the next new alert will notify again.

::note
Keep the `GlobalAlert_NotifyTrigger.postUpdate(OFF)` line at the end of the notify script. It re-arms the trigger for the next alert. If you add a notification action that can throw, wrap it in `try`/`catch` so the reset line still runs.
::

## Build the UI

Add a small alert banner to your overview page. The simplest version uses standard cards:

- `oh-label-card` bound to `GlobalAlert_Message`
- label: `=items.GlobalAlert_Level.state + " · " + items.GlobalAlert_Source.state`
- icon: `alarm`
- visible only when `GlobalAlert_Active` is `ON`
- background colour by level: red for `CRITICAL`, orange for `WARN`, blue for `INFO`
- an **Acknowledge** button that commands `GlobalAlert_Ack` to `ON`
- a **Clear all** button that commands `GlobalAlert_Clear` to `ON`

A compact YAML example for the banner:

```yaml
component: oh-label-card
config:
  item: GlobalAlert_Message
  label: =items.GlobalAlert_Level.state + " · " + items.GlobalAlert_Source.state
  icon: alarm
  visible: =items.GlobalAlert_Active.state === 'ON'
  style:
    background: "=items.GlobalAlert_Level.state === 'CRITICAL' ? '#f44336' : (items.GlobalAlert_Level.state === 'WARN' ? '#ff9800' : '#2196f3')"
    color: white
```

Place the Acknowledge and Clear buttons below it. Hide Acknowledge when `GlobalAlert_Acknowledged` is already `ON`.

## Use it from other rules

### Kitchen heater stale sensor

The live kitchen model currently uses `infra_heat_kuchl_Power`, `kuchl_Temp_TargetMin`, and `kuchl_Temp_TargetMax`; adjust the names if you rename them.

1. Create `infra_heat_kuchl_Alert_Temperature` as a `Switch` in `gAlerts`.
2. Give it metadata: `severity=CRITICAL`, `message=Kitchen heater temperature sensor is stale`.
3. In the heater rule, when the temperature is stale or missing:

   ```text
   infra_heat_kuchl_Alert_Temperature.postUpdate(ON)
   ```

4. When the temperature is fresh again:

   ```text
   infra_heat_kuchl_Alert_Temperature.postUpdate(OFF)
   ```

### Device offline

```text
Switch Zensoria01_Alert_Offline "ZENsoria 01 offline" <alarm> (gAlerts) {
    alert="" [severity="WARN", message="ZENsoria 01 has not reported for 10 minutes"]
}
```

### Runtime limit

```text
Switch Boiler_Alert_Runtime "Boiler runtime" <alarm> (gAlerts) {
    alert="" [severity="WARN", message="Boiler has been on for more than 2 hours"]
}
```

Set the source `ON` while the condition is true and `OFF` when it clears. The controller handles the rest.

## Test it

| Test | Expected result |
|------|-----------------|
| No alerts active | `GlobalAlert_Active = OFF`, count `0` |
| One `WARN` alert goes `ON` | Active `ON`, level `WARN`, message from metadata, count `1`, `logWarn` |
| A `CRITICAL` alert is added | Level becomes `CRITICAL`, count `2`, `logError` |
| The `CRITICAL` alert clears | Level falls back to `WARN`, count `1` |
| All alerts clear | Active `OFF`, count `0`, source and message empty |
| Acknowledge | `GlobalAlert_Acknowledged = ON`, `GlobalAlert_Ack` resets to `OFF`, alert stays active |
| New alert after acknowledge | `GlobalAlert_Acknowledged` resets to `OFF`, notify rule runs |
| Alert Item without metadata | Defaults to `WARN` and the Item label |
| `GlobalAlert_Notify = OFF` | Log only, no external notification |
| `GlobalAlert_Notify = ON` | One notification per new alert, not one per minute |
| openHAB restart | Summary is recomputed from the active source alerts |

## Design notes

- **Use a Group as the bus.** Any Switch can join `gAlerts`; no per-device notification rule is needed.
- **Keep severity in metadata.** The controller stays generic; each alert carries its own severity and message.
- **Acknowledge is not clear.** Ack suppresses notifications but keeps the fault visible. Clear is a manual reset of the source Items.
- **Deduplicate by state change.** Setting an alert `ON` repeatedly does not re-notify. Only a transition to `ON` triggers the notify path.
- **Do not persist only the summary.** If you persist `GlobalAlert_*`, also make sure the source alerts are re-raised after a restart; otherwise the summary can describe an alert that no longer exists.
- **One notification place.** When you add openHAB Cloud, Telegram, or email, change only the notify rule.
- **Alerts are not safety control.** A fault alert is a notification, not a substitute for a fail-safe heater rule or a hardware thermal cutoff.
